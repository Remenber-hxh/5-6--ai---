# 智巡 · 多租户与登录设计方案

> 状态:**待评审**（Vesper 确认后进入实施，边做边讲）
> 范围:后端数据模型 + 鉴权改造 + 移动端登录流程。移动端整体 UI 重构细节另文。

---

## 0. 背景与目标

产品化三个驱动已确认：**持续加功能 / 多用户 / 按客户配置**。叠加领导对登录的要求（不同用户进来能进到对的界面、带对的身份）。据此定两件事：

1. **真多租户**：一套部署、多客户公司共用，数据互相隔离。
2. **登录自动识别身份**：不做手选，账号带出部门 + 角色 + 所属客户，进去自动落到对应首页。

本方案给出这两件事的架构、数据模型、迁移步骤、分阶段路线与风险防线。

---

## 1. 决策速览（TL;DR）

| 议题 | 决策 | 理由 |
|---|---|---|
| 隔离策略 | **共享 schema + `tenant_id` 行级** | 规模小（34 资产 / 558 记录 / 单机）；后端已有 Store 抽象，隔离可在一处收口 |
| 租户来源 | **从登录账号自动带出**，不让用户手选公司 | 少操作、不泄露客户名单；企业微信场景可从企微身份直接确定 |
| 隔离收口点 | **Store 层统一加 `tenant_id` 过滤** | 把"忘加过滤导致串户"的风险摁在一个地方 |
| 角色范围 | 内置角色全局；**自定义角色租户级** | 客户 A 的自定义角色不该出现在客户 B |
| 管理员分级 | **平台超管** vs **租户管理员** 两级 | 你管所有客户，客户只管自己那摊 |
| 登录身份 | **无手选，服务器按账号裁决** | 满足领导意图的同时，杜绝"乱选角色越权"隐患 |
| 落地页 | 登录后**按真实角色自动路由** | 巡检员→拍照台 / 主管→审批 / 管理员→后台 |
| 移动端栈 | React + antd-mobile，与 admin-web 统一 | 共享 API 层 / 类型 / 鉴权 store / 设计令牌 |
| 迁移方式 | 复用版本化迁移器，**纯新增、非破坏** | 存量单租户零感知，可随时回退（有备份） |

## 2. 多租户架构

### 2.1 隔离策略：共享 schema + `tenant_id`

| 方案 | 隔离强度 | 运维/迁移成本 | 结论 |
|---|---|---|---|
| **共享库 + tenant_id 行级** | 应用层保证 | 最低 | ✅ **采用** |
| 每租户独立 schema | 库层保证 | 中 | 规模未到 |
| 每租户独立库 | 物理隔离 | 最高 | 过度设计 |

一套表，每行打客户标签，查询按标签过滤。**应用层隔离的风险是"漏过滤 = 串户"**，用 2.4 的收口设计压住。

### 2.2 哪些表带 `tenant_id`

**带（业务数据，按客户隔离）：**
`users`、`departments`、`assets`、`asset_snapshots`、`records`、`change_requests`、`engineering_tasks`、`engineering_plan_items`、`operation_logs`、`prompt_templates`、`ai_tasks`、`management_ai_reports`、`field_observations`、`field_confirm_logs`

**不带（全局/系统级）：**
`schema_migrations`（迁移账本）、`login_sessions`（挂在用户上，用户已带租户）、`submission_idempotency`（键挂在记录上，记录已带租户）

**角色特例：**
`roles` / `role_permissions` 加 `tenant_id`，但**内置四角色（admin/manager/supervisor/inspector）`tenant_id` 置空 = 全局共享**；自定义角色写入创建者所属租户，只对本租户可见。

### 2.3 租户如何确定（每个请求）

不用子域名，**从登录用户的会话带出**：

```
登录成功 → session 里记 user.tenant_id
后续请求 → 鉴权中间件从 session 取出 tenant_id → 放进请求 context
业务处理 → Store 调用统一带上这个 tenant_id
```

好处：移动端、企业微信内嵌都不用改 URL 结构；一个账号只属于一个租户，天然清晰。

### 2.4 隔离收口点：Store 层

所有租户级查询/写入，在 **Store 层**统一加 `WHERE tenant_id = ?` / 写入时补 `tenant_id`。收口在一处，配合：

- **测试兜底**：加"跨租户不可见"回归用例（A 租户登录读不到 B 的资产/记录）。
- **代码评审清单**：新增任何查询，检查是否带租户过滤。
- 迁移期用 `tenant_id` 可空 → 回填 → 收紧非空约束，分步降风险。

### 2.5 两级管理员

| 角色 | 能干什么 | 边界 |
|---|---|---|
| **平台超管**（你/璟邑） | 建/停客户租户、跨租户运维、看全局 | 唯一能跨租户 |
| **租户管理员**（客户的管理员） | 管本租户的用户/部门/角色/模板/资产 | **只在自己租户内**，看不到别家 |

实现：超管用一个特殊标记（如 `tenant_id = '__platform__'` 或 users 上加 `isPlatformAdmin`）。租户管理员就是当前的 `admin` 角色，但作用域被 `tenant_id` 锁死。

## 3. 登录与身份（领导需求落地）

### 3.1 最终流程：无手选，自动识别

```
① 输账号密码
      ↓
② 服务器认证 → 返回:部门 + 角色 + 权限 + 所属客户(tenant)
      ↓
③ 前端按真实角色自动落到对应首页
   巡检员→拍照台 · 主管→审批中心 · 管理员→后台 · 自定义角色→各归其位
```

登录只有一步，"身份"从"进门前手选"变成"进门后系统按账号自动识别并落地"。

### 3.2 铁律：服务器裁决，前端不越权

角色和权限**永远由服务器按账号下发**，前端不能自报身份。这是安全底线——去掉手选页正是为了消除"乱选角色越权"的隐患。

### 3.3 按角色自动落地页

| 角色 | 默认落地 |
|---|---|
| inspector 巡检员 | 拍照台（移动端主界面） |
| supervisor 复核 | 审批中心 |
| manager 管理 | 管理后台首页 |
| admin 管理员 | 管理后台首页 |
| 自定义角色 | 按其权限矩阵推导首个可访问页 |

### 3.4 后端改动（很小）

登录响应已返回 `user`（含 `roleCode`/`departmentName`）和 `perms`。仅需补两处：

- 登录成功时把 `tenant_id` 写进 `login_sessions`；
- 响应可选加 `defaultLanding`（按角色，几行映射），前端据此自动跳转。

### 3.5 移动端集成 / 企业微信免密（后期）

新 `mobile-web` 与 admin-web 共享鉴权 store，走同一套 `/api/auth/*`。领导说的"移动端集成后端"落点即此。进一步可接**企业微信免密登录**：企微身份 → 映射到租户内用户 → 直接发会话，连密码都不用输。

## 4. 数据模型变更

### 4.1 新增 `tenants` 表

| 字段 | 说明 |
|---|---|
| `id` | 租户 ID |
| `name` | 客户公司名 |
| `code` | 短码（企微/子域名映射备用） |
| `status` | active / suspended |
| `logo` / `theme` | 品牌配置（Phase 3 用） |
| `created_at` | — |

### 4.2 各业务表加 `tenant_id`

见 2.2 清单。统一 `VARCHAR`，建 `(tenant_id, ...)` 复合索引保证过滤性能。

### 4.3 `users` 绑定租户

`users` 加 `tenant_id`；平台超管用特殊值标记。建号时归属到操作者所在租户。

### 4.4 会话带租户

`login_sessions` 加 `tenant_id`（登录时写入），鉴权时读出放进 context。

## 5. 迁移方案（非破坏，复用版本化迁移器）

沿用现有 `migrations.go`（已在生产成功跑过 1–7），**只往后加**：

| 版本 | 内容 | 幂等/安全 |
|---|---|---|
| **008** | 建 `tenants` 表 + 种一个**默认租户（璟邑）** | IF NOT EXISTS |
| **009** | 各业务表加 `tenant_id`（先可空）→ 存量数据**回填默认租户** | 列存在性守卫 + 幂等回填 |
| **010** | 加复合索引；确认回填无残缺后收紧非空约束 | 分步，先索引后约束 |

**存量单租户零感知**：所有老数据归默认租户，现有行为不变。部署前用 `scripts/backup.sh` 先备份（本次已验证可备可还原）。

## 6. 分阶段路线图

> 铁律：每阶段都**不碰在产的旧 `frontend/`**，新东西并行建，达标才切。

| 阶段 | 产出 | 旧版影响 | 风险 |
|---|---|---|---|
| **Phase 0 后端租户地基** | 008–010 迁移、Store 层租户收口、session 带租户、两级管理员、跨租户隔离测试 | 透明，单租户照跑 | 低（纯新增，有备份） |
| **Phase 1 移动端脚手架 + 外壳** | `mobile-web`（React+antd-mobile）脚手架、视口/滚动/安全区地基一次做对、登录（自动识别+自动落地）、共享 API 层 | 无（并行） | 低 |
| **Phase 2 逐屏迁移** | 登录→拍照→识别→字段确认→提交→台账，逐屏对齐旧版 | 无（旧版兜底） | 中（功能对齐） |
| **Phase 3 按客户配置** | 每租户模板/字段/logo/主题；租户配置管理界面 | 无 | 中 |
| **Phase 4 切换** | 生产移动端切新版，退役旧 `frontend/` | 切换 | 中（一次性，可回滚） |

**Phase 0 细分（第一步从这里起）：**
1. `tenants` 表 + 默认租户（008）
2. 各表加 `tenant_id` + 回填（009）
3. session / context 带租户
4. Store 层逐域加过滤 + 跨租户隔离测试
5. 两级管理员与作用域

## 7. 风险与防线

| 风险 | 防线 |
|---|---|
| **数据串户**（漏过滤） | Store 层单点收口 + 跨租户隔离回归测试 + 评审清单 |
| 生产迁移出问题 | 迁移纯新增可空 + 部署前 `backup.sh`（可备可还原已验证） + 迁移失败后端不健康即自动止步 |
| 重构拖垮在产品 | 新旧并行，旧版一直在产兜底，逐屏切 |
| 回退 | 镜像回滚 + 必要时从备份还原库（`restore.sh --force-production`） |

## 8. 相关但不在本方案（领导另提两项）

领导原话还提了"提示词嵌套、工单系统"。这两项**已有基础，属增强不是新建**，建议各自单独评估，别混进本方案免得工期失真：

- **提示词嵌套**：`prompt_templates` + 后台编辑页已有。"嵌套"= 模板可组合/继承（公共片段被多模板引用）——增量增强。
- **工单系统**：异常→待整改→复检→销账闭环（`engineering_tasks`）已在跑。"工单系统"= 在现有闭环上加正式工单壳（编号/指派/时限/流转记录）——增量增强。

## 附：术语

- **租户 tenant**：一个客户公司。数据以 `tenant_id` 隔离。
- **平台超管**：你/璟邑，唯一能跨租户。
- **租户管理员**：客户自己的 admin，作用域锁在本租户。
- **落地页 landing**：登录后按角色自动跳转的首页。
